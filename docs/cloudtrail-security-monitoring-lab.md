\# AWS CloudTrail Security Monitoring Lab



\## Project Overview



This lab demonstrates how AWS CloudTrail can be used to record, review, and investigate account activity for security monitoring and auditing.



The objective was to configure a multi-region CloudTrail trail, deliver management-event logs to Amazon S3, inspect successful API activity, and investigate a denied IAM action generated by a limited-permission user.



The lab focused on practical security visibility: identifying who performed an action, what action was attempted, when it occurred, where it originated, which AWS service processed it, and whether the action succeeded or failed.



\## Environment



\- AWS Region: `us-east-1`

\- Trail name: `cloudtrail-security-monitoring-lab`

\- Trail type: Multi-region

\- Logging status: Enabled

\- Event type: Management events

\- API activity: All

\- Log destination: Amazon S3



\## CloudTrail Configuration



A new CloudTrail trail was created using the AWS Management Console.



Configuration included:



\- Multi-region logging enabled

\- Management events enabled

\- Read and write API activity recorded

\- S3 log delivery configured

\- Trail actively logging



The following features were intentionally left outside the scope of this lab:



\- CloudWatch Logs integration

\- Data events

\- CloudTrail Insights

\- Network activity events



This kept the lab focused on account-level management activity while avoiding unnecessary additional services and cost.



\## Log Storage



CloudTrail was configured to deliver trail logs to an Amazon S3 bucket created during trail setup.



This provides persistent storage for account activity and supports later review, auditing, and investigation.



\## Successful Event Investigation



A successful `CreateTrail` management event was reviewed in CloudTrail Event History.



\### Observed Details



\- Event name: `CreateTrail`

\- Event source: `cloudtrail.amazonaws.com`

\- AWS region: `us-east-1`

\- Read-only: `false`

\- Event category: `Management`

\- MFA authenticated: `true`

\- Source IP address: recorded by CloudTrail

\- User identity: recorded by CloudTrail



The event record also contained request and response information associated with creation of the CloudTrail trail.



This demonstrated that CloudTrail provides visibility into successful administrative changes made within an AWS account.



\## Denied IAM Action Test



To generate a controlled security event, the limited IAM user:



`iam-security-lab-user`



attempted to create a new IAM user named:



`cloudtrail-deny-test-user`



The IAM user did not have permission to perform:



`iam:CreateUser`



AWS rejected the action.



The console returned an authorization error indicating that no identity-based policy allowed the requested `iam:CreateUser` action.



The test user was not created.



\## CloudTrail Investigation of the Denied Action



The denied action was then reviewed from the administrator session using:



`CloudTrail → Event history`



The corresponding event was:



`CreateUser`



\### Event Details



\- User name: `iam-security-lab-user`

\- Event name: `CreateUser`

\- Event source: `iam.amazonaws.com`

\- AWS region: `us-east-1`

\- Error code: `AccessDenied`

\- Read-only: `false`

\- Event category: `Management`

\- MFA authenticated: `true`

\- Source IP address: recorded by CloudTrail



The event record showed that the IAM user attempted to perform `iam:CreateUser` but was not authorized.



This provided direct evidence that CloudTrail records failed administrative activity in addition to successful actions.



\## Security Analysis



The denied `CreateUser` event demonstrated how CloudTrail can support investigation of suspicious or unauthorized activity.



From a single event record, an analyst can determine:



\- Which identity attempted the action

\- Which API operation was requested

\- Which AWS service received the request

\- When the action occurred

\- Which AWS region processed the request

\- The source IP address

\- Whether MFA was used

\- Whether the action succeeded or failed

\- The authorization error associated with the request



This type of information is valuable for auditing, incident response, access reviews, and security investigations.



\## Least-Privilege Validation



This lab also reinforced the IAM least-privilege controls implemented in the earlier IAM Security Lab.



The user:



`iam-security-lab-user`



was intentionally restricted and successfully denied permission to create IAM users.



CloudTrail then provided an auditable record of that denied action.



This demonstrated how IAM authorization controls and CloudTrail logging work together:



`IAM prevents unauthorized actions → CloudTrail records the attempt`



\## Security Outcomes



The completed lab demonstrated:



\- Multi-region CloudTrail configuration

\- Continuous management-event logging

\- S3-based log storage

\- Successful API event investigation

\- Failed API event investigation

\- Detection of `AccessDenied`

\- Visibility into user identity

\- Visibility into source IP address

\- MFA session visibility

\- Auditability of sensitive IAM actions

\- Integration between IAM least privilege and security monitoring



\## Key Takeaways



1\. CloudTrail records AWS API activity and provides detailed audit information.

2\. Successful and failed management actions can both be investigated.

3\. IAM authorization failures can be traced back to the identity that attempted the action.

4\. Source IP, region, event source, API action, and error details are useful during incident investigation.

5\. MFA authentication status can be visible in CloudTrail event records.

6\. Least privilege and logging complement each other: IAM restricts access while CloudTrail provides evidence of attempted activity.

7\. Security controls should be validated with real tests rather than assumed to be working.
